# Network Guard

Настольный монитор подключения для **Windows 10/11 x64**. Помогает собрать признаки сбоя и отличить вероятную проблему локальной сети, DNS, внешнего соединения или HTTP/TLS. Интерфейс, журнал измерений и HTML-отчёт работают локально.

## Что делает

- Проверяет маршрут по умолчанию, локальный IPv4 и доступность шлюза.
- Проверяет внешние узлы через ICMP, TCP 443, DNS и HTTP(S).
- Показывает Wi‑Fi SSID, сигнал, канал и тип радио, если Windows предоставляет эти сведения.
- Собирает информацию об адаптерах, скорости подключения, DNS-серверах и наличии IPv6.
- Считает долю неуспешных ICMP-проверок в скользящем окне и выделяет высокую задержку.
- Фиксирует инцидент после нескольких неудачных циклов и восстановление после возвращения статуса «НОРМА».
- Сохраняет измерения в CSV, события в JSONL и создаёт HTML-отчёты вручную или после восстановления.

Приложение собирает диагностические признаки. Оно не изменяет DNS, маршруты, настройки адаптеров или роутера и не восстанавливает соединение автоматически.

## Готовый EXE без Python

1. Скачайте `NetworkGuard-Windows-x64.zip` из [Releases](https://github.com/Himera2134567/network-guard/releases).
2. Распакуйте архив целиком в папку, в которую можно записывать файлы, например в отдельную папку в «Документах».
3. Запустите `NetworkGuard.exe`. Мониторинг начинается автоматически; кнопки **Старт** и **Стоп** управляют опросом.
4. Настройте интервалы через **Настройки**, а адреса проверок — в `config.json` рядом с EXE.

Python, pip и виртуальное окружение на целевом компьютере не нужны. Встроенные Python, Tk и Tcl включены в один EXE. Обычный запуск не требует прав администратора; системные политики могут ограничивать доступ к сведениям об адаптерах и Wi‑Fi.

Сборка предназначена для Windows x64, не подписана цифровой подписью. Совместимость с другими ОС и Windows ARM64 не проверялась. SHA-256 каждого файла указан в `SHA256SUMS.txt` в релизе.

## Как читать результат

| Код | Значение |
| --- | --- |
| `OK` | Основные проверки доступны. |
| `LOCAL_ROUTE` | Не найден маршрут по умолчанию. |
| `ROUTER_OR_LAN` | Нет ответа от шлюза и внешней сети. |
| `WIFI_OR_ROUTER` | Такая же картина при слабом Wi‑Fi-сигнале. |
| `ISP_OR_UPSTREAM` | Шлюз отвечает, но внешние TCP/HTTP-проверки не проходят. |
| `DNS` | Внешний TCP доступен, DNS-проверка не проходит. |
| `HTTP_TLS_PROXY` | DNS и TCP доступны, HTTP(S)-проверка не проходит. |
| `ICMP_BLOCKED` | ICMP до шлюза и внешних узлов недоступен, остальные проверки проходят. |
| `PACKET_LOSS` / `HIGH_LATENCY` | Повышенная доля неуспешных ICMP-проверок или высокая задержка. |
| `PARTIAL_CONNECTIVITY` / `UNKNOWN` | Смешанные результаты; требуется сопоставление с журналом и другими данными. |

Код причины и уровень уверенности — эвристика. VPN, несколько интерфейсов, фильтрация ICMP, корпоративный прокси и недоступность контрольного сайта могут влиять на вывод. Доля потерь относится к проверочным ICMP-запросам, а не ко всему трафику компьютера. Запросы HTTP(S) используют настройки прокси, которые видит стандартная библиотека Python.

## Настройки и нагрузка

| Параметр | По умолчанию |
| --- | --- |
| ICMP-проверки | Каждые 5 секунд; таймаут 1200 мс. |
| DNS / TCP / HTTP | Каждые 15 секунд; таймаут 2 секунды. |
| Данные Wi‑Fi | Каждые 30 секунд. |
| Маршруты и адаптеры | Каждые 60 секунд. |
| Начало инцидента | После 2 неудачных циклов. |
| Высокая задержка | От 150 мс. |
| Окно ICMP-проверок | 20 измерений; оценка деградации после минимум 6. |

Стандартные адреса проверок: `1.1.1.1`, `8.8.8.8`, `example.com`, контрольные HTTP(S)-страницы Google и Cloudflare. Эти узлы получают обычные диагностические запросы и видят исходящий адрес соединения. Их можно заменить в `config.json`. Интервалы — целевые: медленные системные команды и таймауты увеличивают длительность цикла.

## Данные и отчёты

Рядом с EXE создаются:

- `data/events.jsonl` — изменения состояния и инциденты;
- `data/samples.csv` — измерения;
- `reports/network_report_*.html` — локальные отчёты.

JSONL ротируется после 5 МиБ, CSV — после 20 МиБ; для каждого хранится один предыдущий файл `.1`. Проверка размера выполняется перед записью, поэтому файл может немного превысить порог. HTML-отчёты сохраняются отдельно и автоматически не удаляются.

Журналы и отчёты могут содержать имя компьютера, IP-адреса, SSID, MAC-адреса и параметры адаптеров. Исходные личные журналы и отчёты в этот репозиторий и релиз не включены.

## Структура и технологии

| Файл | Назначение |
| --- | --- |
| `network_guard.py` | Проверки сети, диагностические правила, жизненный цикл инцидентов, хранение данных, HTML-отчёт и интерфейс Tkinter/ttk. |
| `config.json` | Общедоступные настройки по умолчанию без сведений о частной сети. |
| `smoke_checks.py` | Изолированные проверки и создание скрытого окна без запуска сетевого мониторинга. |
| `tests/test_core.py` | Запуск проверок через стандартный `unittest`. |
| `build.py`, `build_exe.bat` | Сборка одного Windows EXE через PyInstaller. |
| `run.bat`, `run_console.bat` | Запуск из исходников с обычным или диагностическим окном. |
| `requirements-build.txt` | Версия упаковщика; сторонних зависимостей во время работы приложения нет. |

Используются стандартная библиотека Python, Tkinter/ttk и штатные команды Windows: `ping`, `route`, `ipconfig`, `netsh`, PowerShell `Get-NetAdapter`.

## Запуск из исходников и сборка

Для исходников нужен Python 3.10+ с Tkinter. Для воспроизводимой сборки используйте **Python 3.12.10+ из ветки 3.12, x64**; выпуск подготовлен на Python 3.12.14 и PyInstaller 6.21.0.

```powershell
python -m pip install -r requirements-build.txt
python -m unittest discover -s tests
python network_guard.py
python build.py
```

Результат сборки — `dist/NetworkGuard.exe`. Для передачи на другой компьютер положите рядом `config.json`. Если файла нет, программа создаёт стандартную конфигурацию.

## Проверки выпуска

```powershell
.\NetworkGuard.exe --self-test --self-test-report .\self-test.json
```

Этот режим использует временные данные: проверяет английский и русский вывод ping, ложный успешный код возврата Windows, OEM-кодировку, диагностические сценарии, начало и восстановление инцидента, экранирование HTML, CSV и ротацию журналов. Затем создаёт скрытое окно с шестью карточками. Реальные сетевые адреса и личные журналы не опрашиваются.

При подготовке 1.0.1 исправлены разбор `мс` и OEM-кодировки Windows, ложное принятие `Destination host unreachable` за успешный ping и фиксация восстановления при неопределённом результате проверок. Полное испытание на всех моделях роутеров, провайдерах и политиках Windows не проводилось.
